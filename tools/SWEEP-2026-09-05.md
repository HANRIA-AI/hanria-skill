# Mutation sweep of the skill scripts, 2026-09-05

`tools/mutants.py`, 678 mutants over the four scripts, run against every step of
`.github/workflows/checks.yml` as it stood at 9649c9a (59 steps).

## First run

678 mutants tested: 361 caught, 303 missed, 14 timeout.

Missed by file:

- check_action.py: 137
- record.py: 88
- _schema.py: 61
- detect_runtime.py: 17

The timeouts are mutations that turn a loop's exit condition false or remove a
bound, so a script reads or loops forever; a step can detect those only by not
finishing. The harness now kills the step's whole process group when that
happens; an earlier build killed only the shell and left the script spinning.

Most survivors fell into three kinds. Refusals reached only through a later
check that refuses the same input for a different reason (the schema pass runs
before the evaluator's own hand checks, and the validator re-checks formats on
values after the schema walk has refused them). Match conditions no request in
the suite ever failed on alone. And outputs no step read: the log's status
object, the digest's own inputs, the reasons of three chain refusals, the
runtime probe's present and unresponsive paths.

## The rule the survivors taught

A step proves a property only when it asserts that property on its own, with
an input that fails for that property and nothing else. A step that asserts
only an exit code proves that something refused, not what or why; a step whose
input also trips an earlier check proves nothing about the later one. Reading a
check shows that it exists and looks like the intended refusal; only a failing
input shows that a test would notice its absence.

## Steps added or tightened

- Every schema refusal is reached on its own, not through a later check (new):
  the schema walk's format refusal under an absent property, an unsupported
  keyword under items, an unsupported type name, boolean-versus-number, each
  validator branch reached directly, the RFC 3339 shape by the schema's own
  prefix, const, enum, minimum items, the depth counter's internals, the
  calendar year read in full, type lists, exact maximum items, three raw
  document refusals by name, a line exactly over the bound, a log without a
  trailing newline, a schema file that is not JSON, and one over the bound.
- Every match condition and every hand check decides on its own (new): kind,
  verb, counterparty, ceiling without an amount, currency, each alone;
  whitespace agent, justification, mandate id, purpose, clause id; an empty
  issuer; non-overlapping clause pairs accepted and one-sided pairs refused as
  overlap; the outcome's mandate, clause, and note; a missing and an
  unreadable mandate; NaN, negative, zero, and non-decimal amounts; origin-only
  and bare-hostname prefixes; a mandate that is an array; a leap second; a
  missing schema file; a duplicated clause id.
- The log's digest, refusals, and status output are pinned (new): frozen
  digest vectors, the append's status object, the rebuilt-log, tampered-count,
  and emptied-log reasons, and the missing-digest refusal.
- Detection reports present and unresponsive endpoints, with their exit codes
  (new): a listening socket, a stale socket file with a colon in its path, and
  an absent one.
- A usage error exits 3, never 2 (tightened): the reason is the usage.
- Past the guard, an interrupt or a closed stdout exits 3 (tightened): an
  interrupt while standard output is a closed pipe, and the closed-pipe cases
  with descriptor 0 closed as well.

One source change: `record.py` returns its `OK` constant where it returned the
literal zero, so the constant's mutant is no longer equivalent.

Three findings about the harness and the steps themselves, each fixed before
the final run: steps wrote fixtures to fixed paths under /tmp, so parallel
mutants clobbered one another (per-copy scratch directories); a step's timeout
killed the shell but not the script it had started, which then spun at full
processor for hours (process groups); and a harness launched as a background
job from a shell inherits an ignored interrupt signal, which no child can then
receive, so the interrupt step waited forever (the signal is reset per step).
The interrupt step's readiness deadline was also widened from twenty seconds to
sixty for slow runners.

## The second run on GitHub, and what the evidence said

Run 33992609681, with each kill's evidence kept: 676 tested, 561 caught, 113
missed, 2 timeouts, in 24 minutes. The two entries the first run had killed
survived this time, as listed, and a third listed entry was killed instead:
`record.py:283:51`, by "Mandate check returns permit, deny and escalate
correctly", a step that never runs the log script. Its evidence shows the
step's exit-code test passing, the printed outcome correct, and the outcome
test, `echo "$out" | grep -q '"outcome": "escalate"'`, returning false, with
nothing on standard error. That is a step failing on its own, once, on a
runner, for a reason the evidence does not establish. A broken pipe does not
explain it: the outcome object is a few hundred bytes, which the shell's echo
hands to the pipe in a single write, so grep has nothing to match until that
write has already landed and cannot close the pipe first. (The same step body
run three hundred times here never failed, but this machine's grep does not
close early on a match, so that loop shows less than it seems.) Two changes
follow, neither claimed as the fix. The
twenty-five outcome tests of that shape are now here-strings, `grep -q ...
<<<"$out"`, which removes the pipe from the pattern; and the harness keeps a
killing step's whole output and exit status rather than a tail, so the next
such kill can be read in full. Every survivor in this run's list is on the
equivalents list. The two entries the first run killed survived this one; that
run kept no evidence, so what failed there is not known, only that it did not
recur.

## The step that had never run under the harness

containers, in the piped form the runner had: the mandate-check step two

The harness itself was then run the same way, on Linux, on the three entries
that were ever killed, expecting them to survive. All three were caught, in
every round, by "Every listed survivor names a mutant that exists and has a
stated reason", the push-gate step added after the second GitHub run and
never yet run under the harness. On this machine the same. The cause was in
the step, not the runner: the list check enumerated mutants from the tree it
ran in, and under the harness that is a copy in which the mutated script has
been re-unparsed, its comments dropped and its line numbers moved, so the
check reported the listed names in that script as missing, all but the few
whose line and column coincide after re-unparsing: 63 of 66 for
`check_action.py`, 31 of 31 for `record.py`, 13 of 14 for `_schema.py`, 5 of
5 for `detect_runtime.py`, counting both lists. Every mutant of a script was
therefore caught by that step, if not by an earlier one. The next dispatch
would not have got that far: its baseline re-unparses all four scripts and
runs every step on them, the list check among them, so the baseline would
have failed on 112 of the 116 listed names and the run stopped with exit 4

a copy.
The harness now names the tree the scripts were read from in
`HANRIA_MUTANTS_SOURCE_TREE` for every step, and the list check reads that
tree when it is named and the checkout otherwise, so it decides the same
question in both places. A step pins the contract:
the check must fail on a copy of the tree with one line inserted at the top
of `check_action.py` and pass on the tree as it is, and it fails with the
fix reverted. The three entries survive again, and every mutant once more on

caught, 114 missed, 2 timeouts, the missed exactly `equivalent.txt` and the
